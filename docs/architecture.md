# Архитектура Team Workspace (предложение)

## 1) Цели архитектуры

- Модульность: независимое развитие чата, задач, календаря и интеграций.
- Надёжность: гарантированная доставка уведомлений и событий.
- Масштабируемость: горизонтальное масштабирование real-time и background workers.
- Безопасность: RBAC, аудит, шифрование на уровне транспорта и хранения.

## 2) Базовые домены

1. **Identity & Access** — пользователи, команды, роли, SSO/OAuth.
2. **Messaging** — чаты, каналы, сообщения, вложения, реакции.
3. **Tasks** — проекты, задачи, статусы, SLA, автоматизации.
4. **Calendar** — события, участники, напоминания, таймзоны.
5. **Mail Integration** — коннекторы, вебхуки, правила обработки.
6. **Notifications** — in-app, push, email digest.

## 3) Технический контур (MVP → scale)

- **Frontend (PWA):** web-клиент с offline shell и push-уведомлениями.
- **API Gateway / BFF:** единая точка входа для веб-клиента.
- **Core services:** messaging, tasks, calendar, notification.
- **Integration service:** адаптеры почтовых провайдеров + нормализация событий.
- **Event bus:** асинхронная связка доменных событий.
- **Storage:**
  - PostgreSQL для транзакционных данных,
  - объектное хранилище для вложений,
  - Redis для кэша/сессий/очередей.

## 4) Сквозные стандарты

- API versioning (`/v1`), idempotency keys для внешних webhook.
- Outbox pattern для гарантированной публикации событий.
- Correlation ID для трассировки запросов.
- Audit log для критичных действий (правила, роли, интеграции).

## 5) Сценарий почтового события

1. Письмо приходит на провайдера.
2. Провайдер отправляет webhook в Mail Integration.
3. Integration service валидирует подпись и нормализует payload.
4. Публикация события `mail.received` в event bus.
5. Notification service отправляет in-app/push.
6. По правилам создаются задача/событие в календаре.
